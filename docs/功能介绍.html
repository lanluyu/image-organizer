1 · 按拍摄时间归档（核心功能）

做什么：把源目录里所有照片视频按「年/月」两级目录归档到目标目录。

python organizer.py --source <源> --target <目标> --duplicates <重复目录>

时间从哪来（四级降级，自动选最权威的）

优先级来源日志标签适用
1缓存命中（ExifTool 预热填充）exiftool-cache多数文件
2ExifTool 单文件查询exiftool缓存未命中
3Pillow 读 EXIFpillow没装 ExifTool 时
4文件修改时间mtime前面都读不到拍摄时间
1.1.0 行为变更

此前 File:FileModifyDate（即文件 mtime）被当作有效的拍摄时间来源，导致任何文件都「有」拍摄时间：Pillow 分支永远走不到，而从 iPhone 拷贝出来、EXIF 已被剥掉的照片会按拷贝时间归到错误年份，日志却显示 source=exiftool，用户完全无从察觉。

现在该字段已移出候选。读不到真实拍摄时间就一路降级到 mtime，并在末尾汇总里计数告警：

1 个文件没有 EXIF 拍摄时间，已按文件系统修改时间归档 ——
若这些文件是拷贝得来的，归档年份可能不是真实拍摄年份

实际效果

输入:  D:/AHAHA/DCIM/Input_Photos/IMG_1234.HEIC   (拍摄于 2024-03-15)
输出:  D:/AHAHA/DCIM/Organized_Photos/2024/03/IMG_1234.HEIC

为什么不按「年/月/日」：照片量大时按月分够用，按日会产生上千个零散文件夹。需要更细可改 imageorg/core.py 里 target_dir 那一行。

2 · 字节级去重（默认开启）

做什么：内容字节完全相同的文件，第二份开始自动移到 duplicates/ 而不是归档目录。无需参数，无法关闭。

算法：size 短路

  1. 先 stat 拿文件大小
  2. size 唯一的文件直接放行 —— 照片几乎不可能字节数完全一样而内容不同
  3. 只对 size 重复的文件算 MD5 比对
1.1.0 修复：跨次运行去重

size 短路放行意味着这个文件的 MD5 从未算过。旧版状态文件只记 {size: []} 空桶，于是第二次运行遇到字节完全相同的副本时，补算出的哈希与空桶比对必然不匹配 —— 分批导入照片时，第二批与第一批的重复会全部漏检。

现在短路放行的文件会把归档后的路径记入 size_pending 欠账表；同 size 文件再次出现时，先回补这些文件的哈希再比对。参照物被用户手工删除时跳过并告警，不影响本次归档。

实际效果

--- 第一次运行 ---
输入: IMG_5678.JPG (100 KB)
输出: 2024/03/IMG_5678.JPG          (size 唯一，短路放行，路径记入欠账)

--- 第二次运行（几天后又导入一批）---
输入: IMG_5678_copy.JPG (100 KB, 内容相同)
输出: duplicates/IMG_5678_copy.JPG  (回补第一次的哈希后比对，判为重复)

典型场景：iPhone 多次「导入到电脑」积累的副本；相同照片被反复拷贝。

3 · 视觉去重（可选，--phash）

做什么：识别「同一张图但不同压缩/分辨率」的相似版本。字节去重抓不到这种（size 不同），需要感知哈希。

python organizer.py ... --phash --phash-threshold 4
  • --phash：启用
  • --phash-threshold N：汉明距离阈值（默认 4），越小越严格。0 = phash 完全相同，4–6 = 视觉极相似

前置依赖：pip install imagehash（没装会报错退出）；pip install pillow-heif（HEIC 解码）。

1.1.0 修复：HEIC 静默失效

Pillow 本身不认 HEIC。此前没有 pillow-heif 依赖，phash_of() 对 .heic 一律返回 None —— 而 iPhone 图库主体就是 HEIC，等于开了 --phash 却对绝大多数文件什么也没做，且没有任何提示。

现在 pillow-heif 已加入 environment.yml 并在启动时注册解码器。若该依赖缺失而你又启用了 --phash，启动时会明确告警：

已启用 --phash，但缺少 pillow-heif: HEIC 文件无法解码，视觉去重对它们不生效
(iPhone 图库主体是 HEIC)。安装: pip install pillow-heif

算法

  1. 用 perceptual hash 算每张图的 64-bit「视觉指纹」（线程池并发解码）
  2. BK-tree 索引找近邻，查询接近 O(log N)
  3. 距离 ≤ threshold 视为视觉重复，整组进 duplicates/

实际效果

输入: photo.jpg            (原图, 5 MB)
      photo_compressed.jpg (压缩版, 800 KB, 同一张照片)
输出: 2024/03/photo.jpg               (归档, phash 入库)
      duplicates/photo_compressed.jpg (距离 0, 视觉重复)
日志: pHash 视觉重复 (dist=0): photo_compressed.jpg ≈ .../2024/03/photo.jpg

典型场景：微信 / iMessage 压缩版与原图共存；从邮件下载的低质量副本。

已知限制：pHash 不区分颜色（DCT 后只看亮度结构），纯色图（200×200 全红 vs 全蓝）会被误判为相同。复杂照片基本不会误判。

4 · Live Photo 配对

做什么：iPhone 实况照片由 IMG_xxxx.HEIC（主图）+ IMG_xxxx.MOV（实况视频）组成。本工具识别同名 HEIC + MOV 为一组，用主图的时间归档到同一目录。默认开启。

为什么重要：两者的 EXIF 时间常常差几秒（拍照瞬间有先后），独立按时间归档可能跨月分到不同目录，破坏 iPhone 重新导入时的实况关联。

输入: IMG_1234.HEIC (EXIF:       2024-02-29 23:59:58)
      IMG_1234.MOV  (CreateDate: 2024-03-01 00:00:01)
输出: 2024/02/IMG_1234.HEIC  ← 用 HEIC 时间决定目录
      2024/02/IMG_1234.MOV   ← MOV 跟随，不独立按 03 月归档

primary 选取规则（同名多文件时谁决定目录）：图片 > 视频 > sidecar，同优先级取首个。

5 · AAE sidecar 跟随 + IMG_E 编辑变体识别

文件含义
IMG_1234.AAE编辑参数（裁剪、滤镜等元数据）
IMG_E1234.JPG/HEIC/AAE「E」前缀 = edited，编辑后的导出版

关键归一化：IMG_E1234 → IMG_1234，所有 stem 相同的文件聚成一组。不归一化的话 IMG_E1234.AAE 与 IMG_1234.HEIC stem 不同，AAE 会被当成独立文件按自身时间戳分到错误月份，破坏编辑参数与原图的关联。

输入: IMG_1234.HEIC   (原图)
      IMG_1234.MOV    (Live Photo 视频)
      IMG_E1234.JPG   (编辑后导出)
      IMG_E1234.AAE   (编辑参数)
输出: 全部归档到 2024/03/ 同一目录

6 · 跨盘原子移动（断电安全）

做什么：source 与 target 在不同硬盘时，用两阶段提交保证移动的原子性，断电不留半成品。默认开启，同盘用 os.replace，跨盘自动切两阶段。

为什么重要：标准库 shutil.move 跨盘时退化成 copy + unlink，非原子。中途断电会留下「目标半成品 + 源完好」，下次扫描会再次「成功归档」源文件，造成永久残留。

跨盘两阶段流程 ① copy 到 target.partial ② fsync 强制刷盘 ← 避免内容还在 page cache 时崩溃 ③ 原子 rename: target.partial → target ④ 删源文件
1.1.0 修复：非跨卷错误被误判

此前用裸 except OSError 判定「跨卷」，于是权限拒绝、目标被占用等同样是 OSError 的错误也会退化成 copy 两阶段 —— 把一个本该失败的移动变成「复制一份再删源」，删源同样失败时会留下两份数据。现在改为判定 errno.EXDEV 或 Windows winerror 17，其它错误原样抛出。

7 · 断点续跑（默认开启）

状态写入 <target>/.organizer_state.json，中断后下次启动自动跳过已处理文件。想从头跑加 --no-resume，或直接删掉状态文件。

状态内容（v3 格式）

{
  "version": 3,
  "size_hashes":  {"123456": ["hash1", "hash2"]},        ← 跨次字节去重
  "size_pending": {"789012": ["D:/tgt/2024/03/a.heic"]}, ← size 短路欠账
  "processed_paths": ["D:/src/IMG_1234.HEIC"],           ← 跳过已处理
  "saved_at": "2026-07-25T15:54:03"
}

版本兼容：v1（无 size 信息）丢弃哈希历史保留断点路径；v2（无欠账表）可直接加载，但那批短路文件的哈希已永久缺失，加载时会告警说明。

何时存盘：每 30 秒心跳、Ctrl+C 时、正常退出时。断电最多丢 30 秒进度。

8 · 中断安全（Ctrl+C）

按下 Ctrl+C 后存盘并以退出码 130 干净退出，下次重复同样命令即可续跑。

1.1.0 修复：保护有洞

此前中断处理只包住主循环，而 MD5 并发计算与 ExifTool 预热都在主循环之前，且常常是整轮里最耗时的部分。那段时间按 Ctrl+C：KeyboardInterrupt 不是 Exception 子类，main() 的兜底接不住 → 直接 traceback 退出、状态不存盘、退出码也不是文档承诺的 130。

现在中断处理上移到 run() 统一收口，覆盖扫描 / MD5 / pHash / 预热 / 主循环全部阶段。后台预热线程通过中止标志在批次间退出，线程池用 cancel_futures 取消排队任务 —— Ctrl+C 不会被几千个已排队任务拖住。

9 · ExifTool 持久进程加速（自动）

读取 EXIF 时不再每文件 fork 一次进程，而是常驻一个 ExifTool 进程通过 stdin/stdout 批量交互，省掉数千次冷启动。只要检测到 ExifTool 可执行文件即自动启用。

文件数每文件 fork持久进程提速
1 0005–8 min30–60 sec~10x
5 00025–40 min2–3 min~13x
10 00050–80 min4–6 min~13x

部署：仓库已自带 Windows 版（./exiftool.exe + ./exiftool_files/），开箱即用。也兼容旧约定 ./exiftool/exiftool.exe。

容错：daemon 崩溃自动重启（最多 3 次），超限后整体降级到 Pillow / mtime，不影响主流程。

10 · 并发计算（MD5 + pHash）

python organizer.py ... --workers 8

默认 4 worker。MD5 与 pHash 都走线程池；ExifTool 预热同时在后台线程跑，与两者重叠，不再串行等待。

计算实测说明
MD52–4xIO 密集，取决于磁盘
pHash2.41x28 张 HEIC / 85.6 MB：串行 6.01s → 8 线程 2.49s

图像解码（整张图解码 + DCT）远比 MD5 昂贵，串行会让 --phash 成为整轮的瓶颈 —— 这是 1.1.0 并发化的主要动因。

11 · Dry-run 预演

python organizer.py ... --dry-run

完整跑一遍流程但不实际移动文件，只打印会做什么：

[DRY-RUN] D:/.../IMG_1234.HEIC -> D:/.../tgt/2024/03/IMG_1234.HEIC
[DRY-RUN] D:/.../IMG_5678.JPG  -> D:/.../dup/IMG_5678.JPG
1.1.0 修复：预演有副作用

此前 mkdir 在 dry-run 判断之前执行，一次预演会在磁盘上创建 target / duplicates 以及完整的年/月空目录树。现在 dry-run 不再创建任何目录，也不写状态文件，多次预演不会污染断点数据。

典型场景：对新目录首次运行前先看一眼分配是否合理；调整 --phash-threshold 后看视觉去重的激进程度。

12 · 单点失败隔离

单个文件失败不会让整个批量任务挂掉，失败收集起来末尾统一打印。

类型含义退出码
FAIL业务失败，如完全读不到时间1
ERROR脚本异常，如 IO 错误、权限拒绝2

  归档成功:   4998
  业务失败:   1
  脚本异常:   1

失败清单 (共 2 条):
  [FAIL]  D:/.../damaged.heic -> 读取时间失败: ValueError: invalid date
  [ERROR] D:/.../locked.jpg   -> stat 失败: PermissionError: ...

13 · 心跳进度

每 30 秒打印一次进度，避免长跑时不知道是卡住还是在跑；同时触发状态盘存。

2026-07-25 15:54:03 | INFO | 心跳 1500/5000 (30.0%)
2026-07-25 15:54:33 | INFO | 心跳 2400/5000 (48.0%)

14 · 退出码语义

退出码含义
0全部成功
1有业务失败（FAIL）
2有脚本异常（ERROR）或参数错误
130用户 Ctrl+C 中断（状态已保存，可续跑）
 
python organizer.py ...
if ($LASTEXITCODE -eq 0)        { Write-Host "全部成功" }
elseif ($LASTEXITCODE -eq 130)  { Write-Host "已中断，明天续跑" }
else { Write-Host "有失败，查看日志"; exit $LASTEXITCODE }

15 · 双击启动（两种）

启动处理照片.bat —— 交互式向导（推荐首次使用）

双击后打开一个 PowerShell 7 窗口，全程引导：

① 说明用途，并明确提示「文件是移动不是复制，源目录会被清空」 ② 依次填写 源目录 / 目标目录 / 重复目录 · 支持从资源管理器直接拖拽路径进来 · 目标与重复目录会给出推荐值，回车即用 ③ 选项：视觉去重（含阈值）· 并发数 · 日志级别 · 每项都带一句说明和推荐值，回车即采用 · 自动检测 imagehash / pillow-heif，装了才提供对应选项 ④ 确认页：待处理文件数与总体积、断点状态、等效命令行 ⑤ 先自动跑一次 --dry-run，看完结果再决定是否真正执行 ⑥ 执行，结束后按退出码给出中文结论

会替你挡掉的错误配置：源目录与目标目录相同、目标与重复目录相同、源目录位于目标目录内部、源目录不存在、源目录里没有可处理的文件。

两个便利功能：

  • 记住配置 —— 确认执行时把本次设置存到 .launcher-config.json，下次启动直接问「沿用上次配置？」，一路回车即可
  • 日志落盘 —— 可选把本次完整输出写到 logs/organizer-yyyyMMdd-HHmmss.log，长跑结束后仍可回看
依赖

需要 PowerShell 7（pwsh.exe）。Windows 自带的 5.1 不适用 —— 没装时 启动处理照片.bat 会直接给出 winget install --id Microsoft.PowerShell 的提示而不是报一堆语法错。

run.bat —— 固定配置一键跑

不交互，预设路径后调用 organizer.py 并打印中文结果摘要。适合路径固定、重复运行的场景。编辑文件顶部三个变量即可：

set "SOURCE=D:\AHAHA\DCIM\Input_Photos"
set "TARGET=D:\AHAHA\DCIM\Organized_Photos"
set "DUPLICATES=D:\AHAHA\DCIM\Duplicates"

默认带 --phash --workers 8。注意它不会先预演，双击即真正移动文件 —— 拿不准时用 启动处理照片.bat。

16 · 完整 CLI 参数表

--source DIR              源目录（必填，待整理的照片所在）
--target DIR              目标目录（必填，按年/月归档到这里）
--duplicates DIR          重复文件目录（必填）
--exiftool PATH           exiftool.exe 路径（默认自动探测）
--dry-run                 只打印不移动（决策前预演）

--phash-threshold INT     pHash 汉明距离阈值（默认 4）
--workers INT             并发 worker 数，作用于 MD5 与 pHash（默认 4）
--no-resume               禁用断点续跑（从头跑）
--log-level LEVEL         DEBUG / INFO / WARNING / ERROR（默认 INFO）
