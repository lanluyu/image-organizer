## 0. 三句话项目摘要

iPhone 照片/视频整理工具。**输入**一个混乱的导出目录，**输出**按"年/月"归档 + 自动去重 + 保留 Live Photo/AAE 配对的整洁结构。**核心价值**是把 iPhone "导入到电脑"得到的几千个平铺文件还原成可维护的结构，并对多次导入产生的重复进行字节级 + 视觉级双重识别。

## 3. 待办清单（按 J 优先级排序）

### P2 — 工程债（建议下次迭代处理）

#### 3.1 HEIC 视觉去重静默失败 ⭐ 高价值低成本

**现象**：`environment.yml` 没有 `pillow-heif` 依赖，`phash_of()` 对 HEIC 文件一律返回 None，但用户大概率以为 iPhone 主力格式 HEIC 在做视觉去重。

**修复**：
1. `environment.yml` 加 `pillow-heif`
2. `organizer.py` 顶部加：
   ```python
   try:
       from pillow_heif import register_heif_opener
       register_heif_opener()
   except ImportError:
       pass
   ```
3. 测试：用 PIL 创建 HEIC 文件验证 `phash_of()` 返回非 None

**预估**：1 turn。

#### 3.2 状态文件改 sqlite

**现象**：`load_state` / `save_state` 用 JSON，10 万张照片后启动会卡几秒读 JSON。

**修复方向**：
- 换 `sqlite3` 标准库（无新依赖）
- 表设计：`size_hashes(size INT, hash TEXT)`、`processed_paths(path TEXT PRIMARY KEY, hash TEXT, target TEXT)`
- 加 v3 状态版本，向后兼容 v2 JSON（首次启动自动迁移）
- 顺便支持新查询：`organizer.py --query <hash>` 反查归档去向

**预估**：3-4 turns。**风险**：状态格式迁移涉及向后兼容，加个 v2→v3 测试。

#### 3.3 拆 src/ 模块

**现象**：`organizer.py` 1187 行，违反全局 `CLAUDE.md` 的 ≤600 行约束。

**修复方向**：
```
src/
├── __init__.py
├── main.py              # CLI + Config 装配 (~80 行)
├── core/
│   ├── exiftool.py      # ExifToolDaemon (~150 行)
│   ├── resolver.py      # DateResolver (~150 行)
│   ├── grouping.py      # FileGroup + group_files + normalize_stem (~80 行)
│   ├── bktree.py        # PHashBKTree (~80 行)
│   ├── hashing.py       # md5_of, phash_of, hamming, _normalize_path_key (~50 行)
│   └── state.py         # load_state, save_state, STATE_VERSION (~80 行)
├── models/
│   ├── config.py        # Config, Stats, FailureRecord (~50 行)
│   └── constants.py     # IMAGE/VIDEO/SIDECAR_EXTENSIONS, DATE_KEYS (~30 行)
└── organizer.py         # Organizer 类 (~400 行)
```

**预估**：4-5 turns，含全套回归。**风险**：所有 `from organizer import X` 的测试 import 都要改。建议保留顶层 `organizer.py` 作为薄包装重新导出，最小化破坏。

### P3 — 易用性 / 鲁棒性

#### 3.4 logs/ 文件输出

**现象**：当前只 `basicConfig` 到 stderr，长跑结果没法回看。违反全局 `CLAUDE.md`。

**修复**：`main()` 在 basicConfig 后加：
```python
logs_dir = Path(__file__).parent / "logs"
logs_dir.mkdir(exist_ok=True)
fh = logging.FileHandler(logs_dir / f"organizer-{datetime.now():%Y%m%d-%H%M%S}.log",
                         encoding="utf-8")
fh.setFormatter(logging.Formatter("%(asctime)s | %(levelname)s | %(message)s"))
logging.getLogger().addHandler(fh)
```

**预估**：1 turn。同时记得 `.gitignore` 加 `logs/`。

#### 3.5 `--reset-state` 命令

**现象**：用户想清空状态从头跑，目前要手动找到 `.organizer_state.json` 删掉。

**修复**：argparse 加 `--reset-state action="store_true"`，在 `Organizer.run()` 开头检测：
```python
if self.cfg.reset_state:
    state_file = self.cfg.target_dir / STATE_FILENAME
    if state_file.exists():
        state_file.unlink()
        self.logger.info("已删除断点状态文件")
```

**预估**：0.5 turn。

#### 3.6 `--verify` 模式

**现象**：用户怀疑 target/ 里某些文件被外部改动（重命名、删除），目前没办法对账。

**修复方向**：扫描 target/，对每个文件算 hash，比对 state.json 中的 size_hashes 集合，输出三类清单：
- state 有 + target 无 → 已删
- state 无 + target 有 → 外部添加
- hash 不匹配 → 内容被改

**预估**：2 turns。

#### 3.7 Windows 长路径支持

**现象**：归档到深层目录可能超 260 字符触发 `OSError`。

**修复**：在 `_atomic_move` / `_iter_files` 中对 Windows 路径自动加 `\\?\` 前缀。注意 `Path` 对象处理 `\\?\` 不完全友好，需要用 `os.path` 字符串操作。

**预估**：1 turn 实现 + 1 turn 测试（mock 长路径）。

#### 3.8 进度条替代心跳

**现象**：30 秒一次心跳信息量低，长跑时不够细。

**修复**：用 `tqdm` 替换 `_heartbeat` + process loop。`tqdm` 是 Pillow 依赖链已有的常用库，加入 environment.yml 成本低。

**预估**：1 turn。**注意**：tqdm 输出会和 logging 互相冲突，需要用 `tqdm.write()` 或 `logging_redirect_tqdm()`。

## 4. 历史踩坑（接手者必读，避免重蹈）

### 4.1 ExifTool `-stay_open` 协议

| 陷阱 | 现象 | 正解 | 测试覆盖 |
|------|------|------|---------|
| `stderr=subprocess.STDOUT` | 诊断行 "X image files read" 混入 stdout 污染 JSON | **必须 `stderr=DEVNULL`** | test_exiftool_daemon.py |
| 加 `-q` 静默 | 看似能压制诊断，但 `{ready}` sentinel 也被压制 → readline 永久阻塞 | **绝对不能加 -q** | 注释明确警告 |
| Windows fsync 句柄模式 | `open(p, "rb")` + `os.fsync` 抛 `EBADF` | 必须 `open(p, "r+b")` 拿可写句柄 | test_atomic_move.py |

### 4.2 IMG_E 编辑变体配对

iPhone 编辑过的照片 sidecar 是 `IMG_E1234.AAE`，主图却是 `IMG_1234.HEIC`，stem 不同。**必须**在 `group_files` 前对 stem 做 `IMG_E → IMG_` 归一化（`normalize_stem` 函数），否则 AAE 会被独立归档破坏关联。

### 4.3 跨卷 `shutil.move` 非原子

`shutil.move` 跨盘退化为 copy+unlink，**非原子**。中途断电留下"目标半成品 + 源完好"，下次扫描会再次"成功归档"造成永久残留。**必须**用 `os.replace`（同卷）或两阶段提交（跨卷）。

### 4.4 size 短路与 README 一致性

旧实现 README 宣称 size 短路省 80% IO，但代码里 MD5 是对所有文件都算的——属于**虚假宣传**。修复后 `_select_hash_candidates` 真正实现 size 短路，README 同步修正。**新功能加文档时必须验证代码确实做到了文档说的**。

### 4.5 状态文件 v1→v2 迁移

旧版状态文件 `processed_hashes: [hash, ...]` 没存 size，无法支持 size 短路。`load_state` 检测到 v1 格式时丢弃 hash 历史（保留 path 用于断点续跑），并打印 warning 提示用户。**改状态格式时务必保留向后兼容**。

### 4.6 patch 类破坏 staticmethod

测试中 `patch("organizer.ExifToolDaemon", return_value=mock)` 会让 `ExifToolDaemon._normalize_key()` 调用返回 MagicMock。**正解**：把归一化逻辑提到模块级函数 `_normalize_path_key()`，所有调用方用模块级，避免被 patch 影响。

## 5. 开发流程建议

### 5.1 修 bug 流程

1. 先在 `tests/` 写一个**失败的回归测试**复现 bug
2. 改代码让测试通过
3. 跑 `pytest tests/ -v` 确认无回归
4. 真实环境验证（如改 daemon 协议必须用真 exiftool 跑）
5. 更新相关文档（README / 功能介绍 / 技术分析）

### 5.2 加功能流程

1. 看 `项目技术分析文档.md` 找最相近的现有抽象
2. 优先扩展现有类而不是加新类
3. 新增模块要提供 `tests/test_xxx.py`，至少覆盖正常路径 + 1 个边界
4. 更新 `功能介绍.md` 的功能矩阵速查表

### 5.3 改测试流程

避免 mock 太多——能用 `tmp_path` 写真实小文件就别 mock filesystem。但**外部进程**（subprocess.Popen）必须 mock，否则跑测试要装 exiftool。

### 5.4 性能优化流程

先 profile（`cProfile` 或加临时 `time.time()` 日志）确认瓶颈，**不要凭直觉优化**。本项目历史上的优化都基于实测数据：
- ExifTool fork 占总时长 ~80% → 上 daemon
- pHash 线性扫描 1 万张 5000 万次 → 上 BK-tree
- size 短路省 80% MD5 IO → 重写候选选择
