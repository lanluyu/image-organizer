0 · 三句话摘要

iPhone 照片/视频整理工具。输入一个混乱的导出目录，输出按「年/月」归档 + 自动去重 + 保留 Live Photo / AAE 配对的整洁结构。核心价值是把 iPhone「导入到电脑」得到的几千个平铺文件还原成可维护的结构，并对多次导入产生的重复做字节级 + 视觉级双重识别。

3 · 待办清单

P2 — 工程债

3.1 状态文件迁 SQLite P2

现象：JSON 状态随文件数无界增长，20 万张照片约 15 MB，启动时全量读取 + 解析。

方向：换 sqlite3 标准库（无新依赖）。表设计 size_hashes(size INT, hash TEXT)、size_pending(size INT, path TEXT)、processed_paths(path TEXT PRIMARY KEY)；升 v4 并保留 v3 JSON 自动迁移。顺便可支持 --query <hash> 反查归档去向。

立项前请注意

旧文档把动因写成「写入太慢」，这个前提已被实测推翻：5 万条路径单次 save_state 仅 73 ms，占 30 秒心跳周期的 0.24%。真实动因是启动读取延迟与文件体积。别再照着错误前提设计。

预估：3–4 turns。风险：格式迁移，需补 v3→v4 测试（v1/v2/v3 的迁移测试已在 test_state_versions.py，照着加即可）。

3.2 processed_paths 何去何从 P2

现象：它只记录移动成功的路径，而这些文件此刻已不在源目录，下次扫描根本扫不到 —— 过滤条件几乎永不命中。唯一生效场景是「把同一份源目录原样拷回来再跑」。代价是无界增长。

这是设计取舍不是 bug，需要你决策后再动：

  • 保留该场景 → 迁 SQLite 后体积不再是问题，顺带把路径 key 归一化（大小写/分隔符）
  • 放弃该场景 → 直接删掉该机制，完全依赖 size+hash 去重，状态文件立刻瘦一大圈

预估：删除 0.5 turn；保留并归一化 1 turn（随 3.1 一起做）。

P3 — 易用性 / 鲁棒性

3.3 logs/ 文件输出

当前只 basicConfig 到 stderr，长跑结果没法回看。在 cli.py 的 main() 里加：

logs_dir = Path(__file__).resolve().parent.parent / "logs"
logs_dir.mkdir(exist_ok=True)
fh = logging.FileHandler(logs_dir / f"organizer-{datetime.now():%Y%m%d-%H%M%S}.log",
                         encoding="utf-8")
fh.setFormatter(logging.Formatter("%(asctime)s | %(levelname)s | %(message)s"))
logging.getLogger().addHandler(fh)

预估：1 turn。注意 .gitignore 加 logs/，以及拆包后 __file__ 要多退一级。

3.4 --reset-state

用户想清空状态从头跑，目前要手动找到 .organizer_state.json 删掉。argparse 加开关，在 Organizer.run() 开头检测并 unlink 即可。预估：0.5 turn。

3.5 --verify 模式

扫描 target/，对每个文件算 hash 与状态里的 size_hashes 对账，输出三类清单：state 有 + target 无（已删）、state 无 + target 有（外部添加）、hash 不匹配（内容被改）。预估：2 turns。

3.6 Windows 长路径支持

归档到深层目录可能超 260 字符触发 OSError。在 _atomic_move / _iter_files 对 Windows 路径自动加 \\?\ 前缀。注意 Path 对 \\?\ 不完全友好，需要 os.path 字符串操作。预估：1 turn 实现 + 1 turn 测试。

3.7 进度条替代心跳

30 秒一次心跳信息量低。用 tqdm 替换 _heartbeat + process loop。注意：tqdm 输出会和 logging 冲突，需要 tqdm.write() 或 logging_redirect_tqdm()。预估：1 turn。

P4 — 测试盲区

3.8 端到端测试固化

1.1.0 期间用一次性脚本做过完整端到端验证（真实 CLI 调用、真实 HEIC 样本、dry-run / 实跑 / 续跑 / 跨次去重四轮），但没有固化成 pytest 用例。建议新增 tests/test_e2e.py，subprocess 调用 organizer.py，断言 target 结构、duplicates 内容、状态文件字段。预估：2 turns。

样本从哪来

image/ 在 .gitignore 里（连同 *.HEIC / *.MOV），克隆下来是没有样本文件的 —— 那是本机的私人照片，不该进公开仓库。tests/test_heic_support.py 已经用 skipif 处理了这种情况，克隆后跑测试会看到 2 项跳过而不是失败。

做 E2E 时别依赖 image/，改用 tests/fixtures/（.gitignore 已为它开了白名单例外），放几张体积极小、可公开的样本。

3.9 心跳 / 汇总打印 / CLI argparse

三块完全无测，但都是 IO 层（基本不变），优先级低。mock time.time() 测心跳判定；caplog 测汇总格式；argparse.Namespace 直接构造测 main()。预估：1 turn。

3.10 覆盖率统计

pytest --cov=imageorg --cov-report=html，加 pytest-cov 依赖。预估：0.5 turn。

4 · 历史踩坑（接手必读）

4.1 ExifTool -stay_open 协议

陷阱现象正解
stderr=subprocess.STDOUT诊断行「X image files read」混入 stdout 污染 JSON必须 stderr=DEVNULL
加 -q 静默连 {ready} sentinel 一起被压制 → readline 永久阻塞绝对不能加 -q
Windows fsync 句柄模式open(p, "rb") + os.fsync 抛 EBADF必须 open(p, "r+b") 拿可写句柄

4.2 IMG_E 编辑变体配对

iPhone 编辑过的照片 sidecar 是 IMG_E1234.AAE，主图却是 IMG_1234.HEIC，stem 不同。必须在 group_files 前对 stem 做 IMG_E → IMG_ 归一化，否则 AAE 会被独立归档破坏关联。

4.3 跨卷 shutil.move 非原子

跨盘退化为 copy + unlink。中途断电留下「目标半成品 + 源完好」，下次扫描会再次「成功归档」造成永久残留。必须用 os.replace（同卷）或两阶段提交（跨卷）。

4.4 文档宣称 ≠ 代码实现

历史上出现过两次同类问题，都是「文档说做了，代码没做」：

  • 旧版 README 宣称 size 短路省 80% IO，实际 MD5 对所有文件都算
  • 1.0.0 README 宣称「断点续跑时跨次去重也走 size 短路」，实际空桶导致跨次重复全部漏检

新功能加文档时必须验证代码确实做到了文档说的。第二个问题藏了两个多月才被发现，因为单次运行内的行为完全正确，只有跨次才暴露。

4.5 「无害的兜底」可能吞掉整条降级链

File:FileModifyDate 被放进 DATE_KEYS 末尾，看起来只是个无害兜底 —— 实际它对任何文件都存在，于是前面所有分支的失败都再也走不到后面：Pillow 分支成死代码，无 EXIF 的照片按拷贝时间归错年份却标注 source=exiftool。

教训：往优先级链末尾加「总是有值」的兜底项时，先问一句「它会不会让链条上游的降级永远不触发」。

4.6 异常层级决定了兜底能不能接住

KeyboardInterrupt 继承 BaseException 而非 Exception。main() 的 except Exception 接不住它 —— 这既是特性（每组处理的 except Exception 不会吞掉 Ctrl+C），也是陷阱（前置阶段的中断会一路穿透，状态不存盘）。加 try/except 时先确认要捕的异常在层级树的哪一支。

4.8 .bat 文件里不能有中文

现象：双击 启动处理照片.bat，窗口一闪就关。手工运行才看到真相：

'wsh；所有交互在' is not recognized as an internal or external command
&& was unexpected at this time.

原因：cmd.exe 每执行完一条命令就按字节偏移回头重读批处理文件。文件里有多字节字符时这个偏移会漂移，cmd 从某一行的中间恢复解析，把残段当成命令执行 —— 上面那句就是从 REM 本文件只负责定位 p|wsh；所有交互在… 中间截断的。

试过的方案结果
加 UTF-8 BOM，保留 chcp 65001仍然崩，BOM 救不了
整篇转 GBK，去掉 chcp仍然崩
整篇纯 ASCII干净通过

约束：启动处理照片.bat 和 run.bat 必须保持纯 ASCII，两个文件顶部都写了这条注释。中文提示一律放进 launcher.ps1（PowerShell 没有这个解析问题），或者由 organizer.py 自己输出。改动后可以这样自检：

$b = [IO.File]::ReadAllBytes('run.bat')
($b | Where-Object { $_ -gt 127 }).Count   # 必须为 0

附带发现：run.bat 从写出来那天起就带着这个毛病，一直没人察觉 —— 因为它执行 organizer.py 那几行恰好没被截断，只有前后的中文提示行在报错刷屏。

4.9 交互循环要有重试上限

launcher.ps1 的目录输入循环在「输入为空」时会重新追问。但当 stdin 已到 EOF（被重定向、管道喂完），Read-Host 立刻返回空字符串 —— 循环空转，几秒就写出 38 MB 输出。所有交互循环现在都有 10 次上限，超限走不读输入的 Stop-Abort 退出（在这种场景下再 Read-Host 等待「按回车关闭」同样会立刻返回，等于换个地方继续死循环）。

4.7 patch 类会破坏 staticmethod

patch("...ExifToolDaemon", return_value=mock) 会让类上的静态方法调用返回 MagicMock。正解：把归一化逻辑提到模块级函数 _normalize_path_key()，所有调用方用模块级，避免被 patch 影响。

5 · 开发流程

5.1 修 bug

  1. 先在 tests/ 写一个失败的回归测试复现 bug
  2. 确认它因为「功能缺失」而失败，而不是因为笔误
  3. 改代码让测试通过
  4. 跑 pytest tests/ -q 确认无回归
  5. 真实环境验证（改 daemon 协议必须用真 exiftool 跑）
  6. 更新相关文档（README / 功能介绍 / 技术分析 / CHANGELOG）

5.2 加功能

  1. 看技术分析找最相近的现有抽象，优先扩展而非加新类
  2. 新模块要有 tests/test_xxx.py，至少覆盖正常路径 + 1 个边界
  3. 更新功能矩阵速查表
  4. 跨模块调用若可能被 mock，走模块属性形式（见技术分析 §8）

5.3 性能优化

先量化再优化，不要凭直觉。本项目历史上的优化都基于实测：

  • ExifTool fork 占总时长 ~80% → 上 daemon（~10x）
  • pHash 线性扫描 1 万张 5000 万次 → 上 BK-tree
  • pHash 串行解码 6.01s / 28 张 → 线程池 2.49s（2.41x）

反例同样重要：save_state 曾被列为瓶颈，实测 5 万条仅 73 ms、占心跳周期 0.24%，据此决定不改。量化的价值一半在于否决伪需求。
