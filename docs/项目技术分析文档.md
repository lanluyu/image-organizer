# Image Organizer — 项目技术分析文档

> 版本：2026-05-10  · 主入口：`organizer.py` (1187 行) · 测试：47 用例全过

---

## 1. 项目定位

iPhone 照片/视频批量整理工具。输入一个混乱的导出目录，输出按拍摄时间归档（`年/月/`）的整洁目录，自动识别重复（字节级 + 视觉级）、保留 Live Photo 和 AAE sidecar 的配对关系、支持中断续跑。

为什么写这个工具：iPhone "导入到电脑" 出来的目录是平铺的几千个文件，跨年跨月混在一起；HEIC + MOV 的 Live Photo 配对、IMG_E 编辑变体、AAE 编辑参数文件之间的关联关系容易被破坏；多次导入容易积累重复。系统自带工具（Photos、文件资源管理器）对这些都没有合理处理。

## 2. 技术栈

| 层 | 选型 | 理由 |
|----|------|------|
| 语言 | Python 3.11 | conda lang 环境；type hints / dataclass / 海象语法 |
| 图像 IO | Pillow | 行业标准；HEIC 走 ExifTool（Pillow 自身不支持） |
| EXIF | ExifTool 13.x（外部 exe） | 覆盖 HEIC/RAW/视频；Pillow 仅 JPEG/PNG |
| 视觉哈希 | imagehash (pHash) | 算法成熟；可选依赖 |
| 测试 | pytest 9.x | unittest.mock 配合 |
| 平台 | Windows 11 + bash/PowerShell | 单一目标平台，`os.name == "nt"` 分支隐藏窗口 |

**软依赖策略**：Pillow / imagehash / ExifTool 都是软依赖，缺失时静默降级。无 ExifTool → Pillow → mtime 三级 fallback；无 imagehash → 拒绝 `--phash` 参数但其他路径不影响。

## 3. 整体架构

```
┌─────────────────┐
│  CLI / run.bat  │  argparse → Config (organizer.py:129)
└────────┬────────┘
         ↓
┌────────────────────────────────────────────────────────────┐
│                      Organizer.run()                        │
│                                                             │
│  ① 扫描 (_iter_files)         排除 target/dup 子树          │
│  ② 扩展过滤                   IMAGE/VIDEO/SIDECAR_EXTENSIONS │
│  ③ 断点续跑过滤                processed_paths 命中跳过      │
│  ④ 分组 (group_files)          IMG_E 归一 + sidecar 跟随     │
│  ⑤ size 短路 (_select_hash_…)  唯一 size 跳过 MD5            │
│  ⑥ 并发 MD5 (_parallel_hash)   ThreadPool, IO 密集          │
│  ⑦ ExifTool prewarm            持久 daemon 批量预热缓存       │
│  ⑧ 串行处理每组 (_process_…)    去重 → 归档 → 移 dup          │
│  ⑨ 收尾                        flush state + close daemon   │
└────────────────────────────────────────────────────────────┘
```

数据流的关键性质：
- **扫描-决策-执行三段分离**：扫描全量结果 → 一次性算 size/MD5/EXIF → 串行 move（避免目标路径冲突）
- **决策阶段尽量批量**：MD5 并发、ExifTool 持久进程、pHash BK-tree 索引——都是为了把"每文件一次系统调用"摊销掉
- **执行阶段串行**：move 是不可逆操作，串行才能正确处理同名冲突（`_unique_path` 加 `_1`/`_2` 后缀）

## 4. 核心模块

### 4.1 数据结构

| 类 | 位置 | 职责 |
|----|------|------|
| `Stats` | organizer.py:106 | 末尾汇总计数（scanned/moved/duplicates/failed/...） |
| `FailureRecord` | organizer.py:121 | 失败记录（path/kind/message），末尾统一打印 |
| `Config` | organizer.py:129 | 运行配置，由 argparse 填充 |
| `FileGroup` | organizer.py:449 | 一组应该一起移动的文件（primary + companions） |

全部用 `@dataclass`，强制 type hints。无 `Any`、无裸 `dict`。

### 4.2 ExifToolDaemon (organizer.py:155)

封装 ExifTool `-stay_open True -@ -` 持久进程协议。

```
启动 → exiftool.exe -stay_open True -@ - -common_args -charset filename=utf8
     stdin=PIPE, stdout=PIPE, stderr=DEVNULL  ← 关键
查询 → 写参数 (每行一个) + "-execute\n" + flush
读结果 → readline 循环到 "{ready}\n" sentinel
关闭 → 写 "-stay_open\nFalse\n" → wait(5s) → terminate(2s) → kill
```

**两个致命陷阱（已踩过并写入测试和注释）**：
1. `stderr=subprocess.STDOUT` 会让诊断行 `"3 image files read"` 混入 stdout 污染 JSON 解析。**必须 DEVNULL**。
2. 加 `-q` 看似能静默诊断，但 **`-q` 会连 `{ready}` sentinel 一起压制**，导致 `readline` 永久阻塞。**绝对不能加**。

崩溃恢复：`_ensure_alive` 检测 `proc.poll()`，已退出则启动新进程，`_restart_count < max_restarts (默认 3)` 才允许，超限抛 `RuntimeError` 让上层降级。

### 4.3 DateResolver (organizer.py:302)

四级降级链：

| 优先级 | 来源 | 标签 | 适用 |
|-------|------|------|------|
| 1 | 缓存命中 | `exiftool-cache` | prewarm 阶段填充 |
| 2 | daemon 单文件查询 | `exiftool` | 缓存未命中（罕见） |
| 3 | Pillow EXIF | `pillow` | JPG/PNG 等 Pillow 支持的格式 |
| 4 | 文件 mtime | `mtime` | 最终兜底，不抛异常 |

**为什么要"prewarm 缓存 + 命中查询"两段式**：
- 直接改 `resolve()` 全批量：调用方改动大、错误处理（每文件 FailureRecord）变复杂
- 直接懒每文件 daemon 查询：失去批量优势，daemon 单次 round-trip 仍有 stdin/stdout 开销
- 当前两段式：prewarm 100 文件/批喂给 daemon，结果填到 dict；resolve() 命中缓存零开销，未命中也走同一 daemon 不再 fork。**调用方零改动 + 性能最优**。

`_daemon_disabled` 旗标：daemon 重启超限后置 True，后续 `resolve` 跳过 daemon 直接走 Pillow，避免每文件都试一次 daemon 重启浪费时间。

### 4.4 PHashBKTree (organizer.py:539)

汉明距离度量空间的 BK-tree，专门用于 pHash 视觉去重的近邻搜索。

**为什么需要**：旧实现每张新图与历史所有 phash 线性 hamming 比对，O(N²)。1 万张照片 ≈ 5000 万次操作。

**算法**：节点 `[hash_int, value, children_dict]`，`children_dict[d]` 是"到当前节点距离为 d"的子树。查询时利用三角不等式 `|d(x,p) − d(y,p)| ≤ d(x,y)`，只递归到 `[d − threshold, d + threshold]` 的子桶。

**复杂度**：理论 O(log N)，实际取决于 hash 分布与 threshold；threshold ≤ 4 时剪枝非常激进。

**正确性验证**：`test_pruning_does_not_miss_neighbors` 用 500 个随机 64-bit hash 与线性扫描对比，必须返回完全相同的近邻集。

### 4.5 group_files (organizer.py:464)

把扁平文件列表分组为 `FileGroup`。聚合 key = `(parent_dir, normalize_stem(stem).lower())`。

**关键归一化**：`normalize_stem` (organizer.py:92) 把 `IMG_E1234` 替换为 `IMG_1234`。iPhone 编辑过的照片 sidecar 是 `IMG_E1234.AAE`，主图是 `IMG_1234.HEIC`，stem 不同——不归一化的话 AAE 会被当成独立 primary 单独归档，破坏与原图的关联。

**primary 选取优先级**：图片 (0) > 视频 (1) > sidecar (2)。同优先级取首个（list sort 稳定）。

### 4.6 Organizer (organizer.py:658)

主调度器，~470 行。run() 是九步流水线（见上方架构图）。关键设计：

- **try/finally 保证 daemon close**：任何路径（正常/Ctrl+C/异常）都关子进程，避免悬挂
- **每组独立 try/except**：单点失败入 `FailureRecord` 继续下一组，不让批量挂掉
- **signal.SIGINT 转 KeyboardInterrupt**：`_on_sigint` 抛 KeyboardInterrupt，外层在干净点位（process loop 间隙）退出
- **心跳 + 周期 flush_state**：30 秒一次进度日志 + 状态盘存，断电最多丢 30 秒进度

## 5. 关键算法

### 5.1 size 短路去重 (organizer.py:768, 783)

**问题**：全量 MD5 每文件读完整内容，IO 密集。

**算法**：
1. `_stat_sizes`：一遍 stat 拿所有 primary 的 size
2. `_select_hash_candidates`：决策哪些需要 MD5
   - size 在历史 `_size_to_hashes` 中出现过 → 必算（可能与历史撞 hash）
   - 当前批次同 size 出现 ≥ 2 次 → 必算（批次内可能重复）
   - 否则 size 唯一 → **跳过 MD5**
3. `_parallel_hash`：只对 candidates 并发算 MD5

**为什么对**：照片几乎不可能字节数完全一样而内容不同——JPEG 压缩、HEIC 编码都把每个文件 size 打散到不同字节数。size 唯一就足以判定"必然不是字节重复"。

**断点续跑配合**：状态文件持久化 `{size: [hash...]}`（v2 格式），跨次去重也走 size 短路。v1 旧格式只有平 hash list、无法 size 短路 → 加载时丢弃 hash 历史并提示用户。

### 5.2 跨卷原子 move (organizer.py:1023)

**问题**：`shutil.move` 跨卷时退化成 copy + unlink，**非原子**。中途断电会留下"目标半成品 + 源完好"，下次扫描会再次"成功归档"源文件，造成永久残留。

**算法**：
1. 先尝试 `os.replace`（同卷原子，跨卷抛 OSError）
2. 跨卷走两阶段：
   ```
   shutil.copy2 (source → target.partial)
   open(partial, "r+b") + os.fsync   ← Windows 必须 r+b 才能 fsync
   os.replace (partial → target)      ← 原子 rename
   os.unlink (source)                ← 删源
   ```
3. 失败清理：copy 阶段失败立刻 unlink `.partial`；rename 后 unlink 失败仅 warning（target 已就位，源残留下次扫描会被识别为字节重复进 dup）

**失败模型完备**：四种崩溃点都不会丢数据（详见代码注释和 README "为什么 move 要分同卷/跨卷"段）。

## 6. 性能优化总览

| 优化 | 位置 | 提速量级 | 代价 |
|------|------|---------|------|
| ExifTool 持久进程 | ExifToolDaemon | **~10-13x** (5000 张 25min → 2-3min) | 协议复杂、stderr/`-q` 陷阱 |
| size 短路去重 | _select_hash_candidates | size 唯一文件 IO 直接归零 | 无 |
| BK-tree 视觉去重 | PHashBKTree | 1 万张 O(N²) → O(log N) | +60 行代码 |
| 并发 MD5 | ThreadPoolExecutor | IO 密集 2-4x | workers 配置 |
| 周期 flush_state | _heartbeat | 断电最多丢 30s 进度 | 30s 一次 JSON 写 |

各优化层正交，不互相依赖。

## 7. 错误处理与容错

### 7.1 多级降级

```
EXIF 读取:     ExifTool daemon → ExifTool 单文件 → Pillow EXIF → 文件 mtime
ExifTool 进程: 启动失败/崩溃 → 重启 (max 3) → 全局 disable → 走后续降级
单文件失败:   FailureRecord 收集 → continue 处理下一组 → 末尾统一打印
状态文件:     损坏 → 警告并重新开始；v1→v2 格式不兼容 → 丢弃 hash 但保留 path
```

### 7.2 单点失败隔离

每个 FileGroup 在 process loop 中独立 try/except：
- 业务失败（读不到时间）→ `FAIL` + `stats.failed`
- 脚本异常（stat/move 失败）→ `ERROR` + `stats.errored`
- 退出码：0 全成功 / 1 有 FAIL / 2 有 ERROR / 130 用户 Ctrl+C

### 7.3 中断安全

| 中断点 | 处理 |
|-------|------|
| Ctrl+C | signal handler 抛 KeyboardInterrupt → 外层 flush_state + return 130 |
| daemon 进程崩溃 | poll() 检测 → 重启 → 超限 disable 继续主流程 |
| 跨卷 move 中途断电 | 两阶段提交，每个阶段失败都可恢复（详见 5.2） |
| 状态文件写入中途崩溃 | tmp + replace 原子写，绝不留半截 JSON |

## 10. 工程哲学体现

对照全局 CLAUDE.md 的工程要求：

| 原则 | 落地 |
|------|------|
| 简单 > 优雅 | BK-tree 自实现 60 行代码而非引入 pybktree 依赖 |
| 接口 > 实现 | `DateResolver.resolve()` 公开签名零改动，prewarm/daemon 全在内部 |
| 可维护 > 一时方便 | 修一个 bug 必加一个回归测试（IMG_E、size 短路、跨卷、daemon 陷阱） |
| 并行 > 串行 | 决策阶段批量并发（MD5、ExifTool prewarm），执行阶段才串行 |
| 可测试性优先 | 关键模块（DateResolver、ExifToolDaemon）支持 mock 注入；FileGroup 是纯数据 |

**违反项**：
- 文件 ≤ 600 行：超了，1187 行（见 P2 技术债）
- 业务逻辑覆盖率 ≥ 80%：未做覆盖率统计，但关键决策路径全有测试
