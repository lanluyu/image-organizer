1 · 项目定位

iPhone 照片/视频批量整理工具。输入一个混乱的导出目录，输出按拍摄时间归档（年/月/）的整洁目录，自动识别重复（字节级 + 视觉级）、保留 Live Photo 与 AAE sidecar 的配对关系、支持中断续跑。

为什么写这个工具：iPhone「导入到电脑」出来的目录是平铺的几千个文件，跨年跨月混在一起；HEIC + MOV 的 Live Photo 配对、IMG_E 编辑变体、AAE 编辑参数之间的关联容易被破坏；多次导入容易积累重复。系统自带工具对这些都没有合理处理。

软依赖策略：Pillow / imagehash / pillow-heif / ExifTool 全部是软依赖，缺失时降级而非崩溃。统一收口在 imageorg/imaging.py，并导出 HEIC_SUPPORTED 供上层判断是否需要提醒用户。

降级 ≠ 静默

1.1.0 的一条设计原则：降级必须可见。缺 pillow-heif 而启用 --phash 会告警；读不到拍摄时间而用 mtime 会计数并在汇总里告警。此前这两处都是静默的，用户拿到错误结果却毫不知情。

3 · 整体架构

organizer.py ← 兼容入口（再导出，保持 from organizer import X 可用） │ ▼ imageorg/ imaging.py 可选依赖收口（Pillow / imagehash / pillow-heif / HEIC_SUPPORTED） constants.py 扩展名集合、DATE_KEYS、心跳间隔、normalize_stem models.py Config / Stats / FailureRecord exiftool.py ExifToolDaemon（-stay_open 协议） dates.py DateResolver（cache → daemon → Pillow → mtime） grouping.py FileGroup / group_files（Live Photo + AAE 配对） dedup.py md5_of / phash_of / hamming / PHashBKTree state.py load_state / save_state（v3，含 v1/v2 迁移） core.py Organizer 主调度 cli.py argparse → Config → Organizer.run()

流水线

Organizer.run() ├─ 建目录（dry-run 时跳过）/ 载入断点状态 / 注册 SIGINT └─ _run_pipeline() ① 扫描 (_iter_files) 排除 target/dup 子树 ② 扩展过滤 SUPPORTED_EXTENSIONS ③ 断点续跑过滤 processed_paths 命中跳过 ④ 分组 (group_files) IMG_E 归一 + sidecar 跟随 ⑤ size 短路 + 前置计算 ├── 后台线程: ExifTool prewarm ┐ ├── 线程池: 并发 MD5 ├─ 三者重叠 └── 线程池: 并发 pHash ┘ ⑥ 串行处理每组 (_process_group) 去重 → 归档 → 移 dup ⑦ 收尾 flush state + 汇总 ⑧ 退出码 中断与 daemon 清理由 run() 的 try/except KeyboardInterrupt + finally 统一收口

数据流的关键性质：

  • 扫描–决策–执行三段分离：扫描全量 → 一次性算 size / MD5 / pHash / EXIF → 串行 move（避免目标路径冲突）
  • 决策阶段尽量批量并重叠：MD5 并发、pHash 并发、ExifTool 持久进程在后台线程 —— 把「每文件一次系统调用」摊销掉
  • 执行阶段串行：move 不可逆，串行才能正确处理同名冲突（_unique_path 加 _1/_2 后缀）

4.2 ExifToolDaemon（exiftool.py）

封装 ExifTool -stay_open True -@ - 持久进程协议。

启动 → exiftool.exe -stay_open True -@ - -common_args -charset filename=utf8 stdin=PIPE, stdout=PIPE, stderr=DEVNULL ← 关键 查询 → 写参数（每行一个）+ "-execute\n" + flush 读结果 → readline 循环到 "{ready}\n" sentinel 关闭 → 写 "-stay_open\nFalse\n" → wait(5s) → terminate(2s) → kill
两个致命陷阱（已写入测试与注释）

① stderr=subprocess.STDOUT 会让诊断行 "3 image files read" 混入 stdout 污染 JSON 解析 —— 必须 DEVNULL。

② 加 -q 看似能静默诊断，但 -q 会连 {ready} sentinel 一起压制，导致 readline 永久阻塞 —— 绝对不能加。

崩溃恢复：_ensure_alive 检测 proc.poll()，已退出则启动新进程；_restart_count < max_restarts（默认 3）才允许，超限抛 RuntimeError 让上层降级。

4.3 DateResolver（dates.py）

优先级来源标签适用
1缓存命中exiftool-cacheprewarm 阶段填充
2daemon 单文件查询exiftool缓存未命中（罕见）
3Pillow EXIFpillow没装 ExifTool 时
4文件 mtimemtime最终兜底，不抛异常

为什么要「prewarm 缓存 + 命中查询」两段式：

  • 直接改 resolve() 全批量 → 调用方改动大，每文件的 FailureRecord 错误处理变复杂
  • 纯懒式每文件 daemon 查询 → 失去批量优势，单次 round-trip 仍有 stdin/stdout 开销
  • 当前两段式：prewarm 每批 100 文件喂给 daemon，结果填进 dict；resolve() 命中缓存零开销，未命中也走同一 daemon 不再 fork。调用方零改动 + 性能最优

_daemon_disabled 旗标：daemon 重启超限后置 True，后续 resolve 跳过 daemon 直接走 Pillow，避免每文件都试一次重启浪费时间。

1.1.0 新增：prewarm(should_abort=...) 批次间中止钩子。prewarm 现在跑在后台线程里，可能持续几分钟，用户 Ctrl+C 时必须能在一个批次（~100 文件）内退出，而不是拖住整个进程。

4.4 PHashBKTree（dedup.py）

汉明距离度量空间的 BK-tree，用于 pHash 视觉去重的近邻搜索。

为什么需要：旧实现每张新图与历史所有 phash 线性比对，O(N²)。1 万张照片 ≈ 5000 万次 hamming 计算。

算法：节点 [hash_int, value, children_dict]，children_dict[d] 是「到当前节点距离为 d」的子树。查询时利用三角不等式 |d(x,p) − d(y,p)| ≤ d(x,y)，只递归到 [d − threshold, d + threshold] 的子桶。

复杂度：理论 O(log N)，实际取决于 hash 分布与 threshold；threshold ≤ 4 时剪枝非常激进。

正确性验证：test_pruning_does_not_miss_neighbors 用 500 个随机 64-bit hash 与线性扫描对比，必须返回完全相同的近邻集。

4.5 group_files（grouping.py）

把扁平文件列表分组为 FileGroup。聚合 key = (parent_dir, normalize_stem(stem).lower())。

关键归一化：normalize_stem 把 IMG_E1234 替换为 IMG_1234。iPhone 编辑过的照片 sidecar 是 IMG_E1234.AAE，主图是 IMG_1234.HEIC，stem 不同 —— 不归一化的话 AAE 会被当成独立 primary 单独归档，破坏与原图的关联。

primary 选取优先级：图片 (0) > 视频 (1) > sidecar (2)，同优先级取首个（list sort 稳定）。

4.6 Organizer（core.py，589 行）

  • run() / _run_pipeline() 分离：前者负责建目录、载状态、注册信号、中断收口与 daemon 清理；后者是纯流水线。这样中断处理只写一处，覆盖全部阶段
  • 每组独立 try/except：单点失败入 FailureRecord 继续下一组。捕的是 Exception，KeyboardInterrupt 是 BaseException 不会被吞
  • _parallel_map 共用 helper：MD5 与 pHash 共享同一并发骨架，退出时 shutdown(wait=False, cancel_futures=True)，Ctrl+C 只等在跑的那几个任务
  • 心跳 + 周期 flush_state：30 秒一次进度日志 + 状态盘存，断电最多丢 30 秒进度

5 · 关键算法

5.1 size 短路去重 + 欠账回补

问题：全量 MD5 每文件读完整内容，IO 密集。

  1. _stat_sizes：一遍 stat 拿所有 primary 的 size
  2. _select_hash_candidates：决策哪些需要 MD5
    • size 在历史 _size_to_hashes 或 _size_pending 中出现过 → 必算
    • 当前批次同 size 出现 ≥ 2 次 → 必算
    • 否则 size 唯一 → 跳过 MD5
  3. _parallel_hash：只对 candidates 并发算 MD5

为什么对：照片几乎不可能字节数完全一样而内容不同 —— JPEG 压缩、HEIC 编码都把每个文件 size 打散。size 唯一就足以判定「必然不是字节重复」。

1.1.0 修复的正确性缺口

短路放行意味着该文件的 MD5 从未算过。旧实现只写入 {size: set()} 空桶并持久化为 {"size": []}。于是：

第 1 次运行: a.jpg (12345 字节, size 唯一) → 短路放行, state = {12345: []} 第 2 次运行: b.jpg (与 a.jpg 字节完全相同) size 12345 在历史中 → 补算 MD5 = H bucket 为空集 → H 不在其中 → 判为新文件，重复漏检 ✗

README 曾宣称「断点续跑时跨次去重也走 size 短路」，实际不成立。分批导入照片时，第二批与第一批的重复会全部漏检。

解法：新增 size_pending: {size: [归档后路径]} 欠账表。短路放行的文件在移动成功后把目标路径记入欠账；同 size 文件再次出现时，_backfill_pending(size) 先对欠账路径补算 MD5 折进桶里再比对。参照物已被用户手工删除时捕 OSError 跳过并告警 —— 不是本次处理的文件，不记为失败。

为什么不干脆全算 MD5：那就放弃了短路优化本身。欠账表只在「size 恰好出现过一次」时才有条目，规模远小于全量哈希表，且空桶不写盘（save_state 过滤空列表）。

5.2 跨卷原子 move

问题：shutil.move 跨卷时退化成 copy + unlink，非原子。中途断电会留下「目标半成品 + 源完好」，下次扫描会再次「成功归档」源文件，造成永久残留。

① os.replace(source, target) 同卷原子，一步到位 └─ 抛 OSError 且 errno == EXDEV 或 winerror == 17 → 跨卷，走 ② 其它 OSError（权限拒绝等）→ 原样抛出 ← 1.1.0 修正 ② shutil.copy2(source, target.partial) ③ open(partial, "r+b") + os.fsync Windows 必须 r+b 才能 fsync ④ os.replace(partial, target) 原子 rename ⑤ os.unlink(source) 删源

失败模型完备：

崩溃点残留下次扫描的结果
② copy 中途.partial + 源完好重做即可
③ fsync 后 / ④ rename 前同上重做即可
④ rename 后 / ⑤ unlink 前target 已成形 + 源残留源被识别为字节重复进 duplicates，不丢数据
（旧实现）shutil.move 跨卷 copy 中途target 半成品 + 源完好源被「成功」归档，半成品永久残留 ✗
1.1.0 修正：EXDEV 判定

此前第 ① 步用裸 except OSError: pass。权限拒绝、目标被占用等同样是 OSError，会被误当作跨卷而退化成 copy 两阶段 —— 把一个本该失败的移动变成「复制一份再删源」；若删源同样因权限失败，就留下两份数据。现在只有 errno.EXDEV（或 Windows winerror 17）才走两阶段。

5.3 时间来源判定

DATE_KEYS 按权威性排序，_parse_exif_record 取第一个能解析的字段。

1.1.0 修正：File:FileModifyDate 已移出候选

该字段对任何文件都存在（它就是 mtime）。一旦纳入候选，_parse_exif_record 永远有返回值，于是：

  • _from_pillow 成为死代码，永远走不到
  • 从 iPhone 拷出、EXIF 被剥掉的照片按拷贝时间归到错误年份
  • 日志标注 source=exiftool，用户以为读到了真实拍摄时间

现在没有真实拍摄时间就一路降级到 mtime，由 source 标签如实反映，Stats.date_from_mtime 计数，汇总末尾发 WARNING。query_batch 也不再请求该字段。

7 · 错误处理与容错

EXIF 读取: ExifTool daemon → ExifTool 单文件 → Pillow EXIF → 文件 mtime（计数告警） ExifTool 进程: 启动失败/崩溃 → 重启（max 3）→ 全局 disable → 走后续降级 HEIC 解码: 缺 pillow-heif → phash 返回 None → 启用 --phash 时启动告警 单文件失败: FailureRecord 收集 → continue 下一组 → 末尾统一打印 状态文件: 损坏 → 警告并重新开始；v1 → 丢弃 hash 保留 path；v2 → 加载并告警欠账缺失

中断安全

中断点处理
Ctrl+C（任意阶段）signal handler 置 _abort 并抛 KeyboardInterrupt → run() 统一 flush_state + 返回 130
Ctrl+C（后台 prewarm 线程）线程在批次间检查 _abort 退出，最多滞后一个批次（~100 文件）
Ctrl+C（线程池排队任务）shutdown(wait=False, cancel_futures=True) 取消排队，只等在跑的
daemon 进程崩溃poll() 检测 → 重启 → 超限 disable 后继续主流程
跨卷 move 中途断电两阶段提交，每个崩溃点都可恢复（见 5.2）
状态文件写入中途崩溃tmp + replace 原子写，绝不留半截 JSON
1.1.0 修复：中断保护有洞

旧实现的 try/except KeyboardInterrupt 只包住主循环，而 MD5 并发与 ExifTool 预热都在主循环之前，且常常是整轮最耗时的部分。那段时间中断：KeyboardInterrupt 不是 Exception 子类 → 穿透 run() 的 try → 穿透 main() 的 except Exception → traceback 退出、状态不存盘、退出码非 130。

写回归测试时这个缺陷表现得很直观：patch.object(org, "_parallel_hash", side_effect=KeyboardInterrupt) 直接把整个 pytest 会话打断了。

设计原则

  • mock 外部进程：ExifTool 用 MagicMock(Popen)，不依赖真实 exe
  • 真实文件 IO：tmp_path 写真实小文件，不 mock filesystem（避免 mock 错位）
  • 每个修过的 bug 都有专用回归测试：IMG_E 配对、size 短路、跨次去重、跨卷两阶段、BK-tree 剪枝、dry-run 副作用、中断覆盖
patch 目标与模块边界

拆包后 patch("organizer.md5_of") 这类目标全部失效 —— 打在兼容入口的名字上不会影响 imageorg.core 里的查找。现在的约定是：被测试 patch 的名字必须通过模块属性访问（dedup.md5_of(...)、imaging.HEIC_SUPPORTED、exiftool.ExifToolDaemon(...)），测试则 patch imageorg.<模块>.<名字>。新增可被 mock 的跨模块调用时请沿用这个写法。

未覆盖：心跳、汇总打印、CLI argparse（IO 层，由端到端手工验证兜底）。

关于 processed_paths

它只记录移动成功的文件路径 —— 而这些文件此刻已不在源目录，下次扫描根本扫不到，过滤条件几乎永不命中。唯一真正生效的场景是「把同一份源目录原样拷回来再跑」。代价是它随文件数无界增长（20 万条约 15 MB）。

这是设计取舍不是 bug：要么承认这个场景并接受体积（迁 SQLite 后不成问题），要么去掉该机制、完全依赖 size+hash 去重。需要决策后再动。同理，它的路径 key 没做大小写/分隔符归一化 —— 但因为没有可观测行为，写不出有意义的失败测试，1.1.0 未改动。
